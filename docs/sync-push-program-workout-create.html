Sync push spec: create a program and its workouts

How the client asks the server to create one PROGRAM row and its WORKOUT rows, what the server does with the request, and what it returns. This step covers creation only.

4. Values per resource type

A create sends every field of the row. A key that is left out is treated as null. The server rejects any key that the table does not list.

PROGRAM values

KeyTypeRequiredRuleEntity field

The length rules match the check constraints on the entities. Validating them in the service gives the client a 400 response before the database rejects the row.

5. Server processing

The whole request runs in one transaction.

  1. Lock the user. Take the per-user exclusive lock before anything else, so change log sequences commit in the order they were assigned.
  2. Validate the whole request. Check the shape, the resource types, baseVersion = 0, and the values for every change. If anything fails, return 400 and apply nothing.
  3. For each operation, in order:
    1. Already applied? Look up sync_change_log by (user_id, operation_id). If the row exists, build an APPLIED result from it and move to the next operation. Do not apply the changes again.
    2. Check for conflicts. A create conflicts when a row with that resourceId already exists for this user. Collect every conflicting change.
    3. On conflict, stop. Add one CONFLICT result for this operation and return. Do not process later operations. Operations already applied in this request stay applied.
    4. Apply. Create the Program and Workout entities from the values and save them.
    5. Flush and read versions. @Version is written at flush, so call flush() before reading the versions for the result.
    6. Write the change log. Insert one SyncChangeLog row. Its sequence goes into the result.
    7. Add an APPLIED result.
  4. Commit and return the results.

Why stop at the first conflict: the client rejects any result that comes after a conflict. Later operations may also depend on the one that conflicted, for example an update to a program whose create failed.

Retry

The client did not receive the response and sends the same request again. Step 3a finds operation a1c9… in the change log, so the server returns the same APPLIED result with sequence: 42 and creates nothing.

7. Errors

StatusWhen
400Malformed JSON, a missing required field, an unknown resourceType, a changeKind other than CREATE, baseVersion other than 0, a duplicate resource in one operation, an invalid or unknown value key, or a resource ID that belongs to another user. Nothing is applied.
401X-User-Id is missing or no such user exists.

Checked exceptions do not roll back a @Transactional method. Throw unchecked exceptions such as IllegalArgumentException and map them to 400 in a @RestControllerAdvice.

The stored change has version, the version after the change. The pushed change has baseVersion, the version the client started from. For a create, store every field, including those that were left out as null, so a device that pulls this change can build the whole row.

11. Choices made in this spec

Each of these could go another way. Change them if you disagree.

ChoiceAlternativeWhy this one
Validate the whole request first and return 400 for any problem Report the error per operation in results The client has no "error" status. A malformed request is a bug, not a state to recover from.
Reject unknown value keys Ignore them Jackson ignores unknown keys by default, so a misspelled key would disappear without an error.
One transaction per request One transaction per operation Simpler. Per-operation transactions hold the lock for less time and commit partial progress. Consider them when requests get large.
Uppercase status names Keep the client's lowercase names Matches the uppercase rule for resource types and change kinds, and maps directly to a Java enum.

12. Open decisions

Version after create. The client requires version ≥ 1 in an APPLIED result, and treats 1 as the first server version. VersionedEntity inserts rows at version 0. Decide whether to store versions starting at 1, or keep 0 in the database and add 1 everywhere a version leaves the server.

Program row fields do not match. The client has trainingMode and the server has no column for it. The server has progressStartedAt and the client never sends it. Decide where each field lives before the program values are final.

Create on a deleted ID. If sync_tombstones already has the resource, decide whether the create is a conflict or a 400. With random UUIDs this only happens through a client bug.

Device registration. Decide whether push creates the SyncDeviceState row for an unknown deviceId or rejects the request until the device is initialized.
